## 简介
mcp-go-x402 库为 MCP-Go 客户端和服务器提供 x402 支付协议支持，允许在调用工具时进行自动支付处理。该库支持多种签名方式，包括私钥、助记词和加密的 keystore 文件。由于涉及区块链资产的支付授权，安全考虑至关重要。本指南重点讨论使用该库时必须注意的关键安全问题，包括私钥管理、支付审批流程、网络验证以及库本身提供的安全机制。

## 私钥管理最佳实践

在使用 mcp-go-x402 时，正确管理私钥、助记词和 keystore 文件是防止资产被盗的首要防线。该库提供了 `PrivateKeySigner`、`MnemonicSigner` 和 `KeystoreSigner` 三种签名器，每种都对应不同的密钥管理方式。

### 安全存储与访问
- **避免硬编码**: 绝对不要在代码中硬编码私钥、助记词或 keystore 密码。将这些敏感信息作为环境变量注入，或使用专门的密钥管理服务（KMS）。
- **使用加密的 Keystore**: `KeystoreSigner` 使用 `go-ethereum` 的 `keystore.DecryptKey` 方法来解密 JSON 格式的 keystore 文件。这要求用户提供密码，为私钥提供了额外的加密保护层。应始终使用强密码来加密 keystore 文件。
- **助记词的安全**: `MnemonicSigner` 接受一个 BIP-39 标准的助记词短语。助记词等同于私钥，一旦泄露，所有关联资产都将面临风险。必须使用 `bip39.IsMnemonicValid` 函数验证助记词的有效性，并确保其存储在安全的离线环境中。

### 初始化签名器
当创建签名器时，库会立即解析并加载私钥到内存中。例如，`NewPrivateKeySigner` 函数会将十六进制字符串解码为字节，再转换为 `ecdsa.PrivateKey` 对象。此过程必须在安全的环境中进行，确保输入的私钥来源可靠。

## 支付审批流程风险分析

支付审批流程可能面临中间人攻击（MitM）和签名伪造等风险。mcp-go-x402 通过采用 EIP-712 签名标准来有效缓解这些威胁。

### 中间人攻击与签名伪造
在传统的纯消息签名中，攻击者可能截获一个有效的签名，并将其重放或用于其他交易。由于签名内容不包含上下文，服务器难以验证该签名是否是为特定交易而生成的。

### EIP-712 签名的缓解作用
mcp-go-x402 在 `SignPayment` 方法中实现了 EIP-712 标准化签名。EIP-712 通过以下方式增强安全性：
1.  **结构化数据**: 签名的数据是结构化的 JSON 对象，包含 `EIP712Domain` 和 `TransferWithAuthorization` 类型。
2.  **上下文绑定**: `EIP712Domain` 包含 `name`、`version`、`chainId` 和 `verifyingContract` 字段。这确保了签名只能在指定的区块链网络（通过 `chainId`）和特定的合约（`verifyingContract`，即资产地址）上被验证。
3.  **防重放**: 授权消息中包含 `validAfter` 和 `validBefore` 时间戳，定义了签名的有效时间窗口。此外，`nonce` 字段（由时间戳、资源和地址生成）确保了每个签名的唯一性，防止重放攻击。

通过这种方式，即使攻击者获取了签名，也无法将其用于其他网络、其他合约或在有效时间窗口之外使用。

## 网络验证的重要性

确保客户端连接到正确的区块链网络是防止资产损失的关键。连接到错误的网络（如测试网）可能导致资金被发送到无法找回的地址。

### 客户端侧的网络验证
mcp-go-x402 库通过 `ClientPaymentOption` 结构体中的 `ChainID` 字段来实现网络验证。当客户端收到支付请求时，`SignPayment` 方法会首先调用 `GetPaymentOption` 来查找匹配的支付选项。如果找到，它会检查该选项的 `ChainID` 是否已配置。如果 `chainID` 为 `nil`，则会返回错误，阻止签名操作。

这种机制强制开发者在创建签名器时明确指定支持的网络及其对应的链 ID（例如，Base 主网的 `8453`）。这确保了签名只能在预配置的、受信任的网络上进行。

## 内存保护与敏感数据清理

虽然 Go 语言的垃圾回收机制会自动管理内存，但敏感数据（如私钥）在内存中驻留的时间越长，被恶意软件或内存转储工具窃取的风险就越高。mcp-go-x402 库通过其设计在一定程度上增强了内存安全。

### 库的内存保护机制
在 `signer.go` 的实现中，私钥 (`privateKey *ecdsa.PrivateKey`) 作为 `PrivateKeySigner` 结构体的一个字段被持有。该私钥在签名器的整个生命周期内都存在于内存中，用于执行 `SignPayment` 操作。

库本身没有显式地在签名后立即“擦除”私钥内存的代码。这是因为 Go 的内存管理模型使得精确控制特定内存块的清理非常困难。然而，库通过以下方式间接增强了安全性：
- **最小化暴露**: 私钥仅在 `SignPayment` 方法内部用于 `crypto.Sign` 调用，这是与私钥交互的唯一地方。
- **依赖底层库**: `crypto.Sign` 函数来自 `go-ethereum` 库，其内部实现可能包含对敏感操作的保护。

### 开发者责任
开发者应意识到，只要签名器实例存在，其私钥就存在于内存中。最佳实践是：
- **限制签名器生命周期**: 在完成必要的支付操作后，应尽快丢弃签名器实例，使其可以被垃圾回收。
- **避免不必要的日志记录**: 绝对不要记录包含私钥或签名数据的结构体。

## 安全检查清单

在部署使用 mcp-go-x402 的应用前，请使用以下检查清单评估其安全状况：

| 检查项 | 描述 | 状态 |
| :--- | :--- | :--- |
| **私钥存储** | 私钥、助记词或 keystore 密码是否硬编码在源代码中？ | ☐ |
| **环境变量** | 敏感信息是否通过环境变量或安全的密钥管理服务提供？ | ☐ |
| **Keystore 加密** | 如果使用 keystore 文件，是否使用了强密码进行加密？ | ☐ |
| **EIP-712 签名** | 是否确认库使用了 EIP-712 签名来绑定交易上下文？ | ☐ |
| **网络验证** | `ClientPaymentOption` 是否配置了正确的 `ChainID` 以防止跨链攻击？ | ☐ |
| **支付回调** | 是否实现了 `PaymentCallback` 来根据金额和资源手动批准大额支付？ | ☐ |
| **签名器生命周期** | 签名器实例是否在使用后被及时丢弃？ | ☐ |
| **依赖更新** | `go-ethereum` 和 `go-bip39` 等关键依赖是否保持最新？ | ☐ |
